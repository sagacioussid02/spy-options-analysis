Autopilot desk: architecture and constraints

A cron-triggered CCR session runs a deterministic engine, a three-agent debate, and (conditionally) a live order — all through an egress-restricted sandbox that can't open a raw TCP socket, which is the constraint that actually shaped this design. Below: the wire-level mechanism, the stack, and what's actually armed right now.

Mechanism

Three write paths converge on one Postgres instance and one broker. Only one of them is currently live.

Stack

Grouped by layer, with the non-obvious choice behind each one — this is the part that doesn't show up in a box-and-arrow diagram.

Trigger / compute

Claude Code Routines (CCR)

Cron-scheduled cloud sessions; each fire is a fresh git clone into an ephemeral sandbox — no filesystem state survives between runs.

Why not a VM/Lambda: zero infra to own, and the routine already has Claude Code's own tool loop (Bash, background tasks) for orchestrating multi-minute subprocess chains.

Network boundary

Egress proxy, Custom allowlist

Outbound traffic routes through a policy-enforcing HTTPS forward proxy with TLS re-termination (custom CA bundle). Default "Trusted" level allows package registries only; we set Custom + *.yahoo.com, cma-store-proxy.vercel.app.

The constraint that drove everything below: this proxy is HTTP-only — it does not pass through arbitrary TCP, so raw Postgres on 5432 is unreachable no matter what's on the domain allowlist. Confirmed empirically: curl to an allowlisted HTTPS host worked immediately; psycopg3.connect() to an allowlisted Postgres host hung to timeout.

Agents

Claude Managed Agents (CMA)

Bull/Bear/PM run as three separate hosted sessions (Anthropic Messages API, claude-haiku-4-5), each with its own tool grants — Robinhood reads via an MCP toolset, web_search, and custom tools (propose_trade, submit_case).

Why three sessions, not one model role-playing three parts: a single context that generates both the bull and bear case tends toward self-agreement. Separate sessions — the Bear only receiving the Bull's finished output — produce a genuine adversarial check.

Broker integration

Robinhood Trading MCP

streamable-http MCP transport at agent.robinhood.com/mcp/trading. OAuth2 with PKCE; refresh-token rotation handled two ways — CMA's vault proxy for hosted sessions (credential never enters the sandbox), and a local refresh_robinhood_token() for host-side script calls.

Why two refresh paths coexist: the vault's copy and the local .env/store copy of the refresh token can drift out of sync since OAuth refresh tokens are typically single-use — a known open item, not yet unified.

State bridge

store_proxy — Vercel, Python runtime

A stateless BaseHTTPRequestHandler function (no framework) exposing GET/PUT /api/store?name=<collection>, bearer-token gated, holding the real DATABASE_URL and doing the psycopg3 call itself — since Vercel functions have unrestricted egress.

Why not Neon's Data API (PostgREST): evaluated first — provisioned it, then found its auth model requires Neon Auth (Stack Auth, a full end-user identity system) or an externally-hosted JWKS endpoint for service-to-service calls. Disproportionate for one internal caller; reverted in favor of a token we control.

HTTP client hardening

requests + Connection: close

First live run threw intermittent SSLError: UNEXPECTED_EOF_WHILE_READING from Python's requests/urllib3 against the proxy — while curl against the identical URL, same process, succeeded 5/5. Fixed with an explicit Connection: close header (no pooled reuse) plus a 3-attempt backoff retry.

Root cause, inferred not confirmed: urllib3's connection pool reusing a CONNECT-tunneled socket to the proxy after it had gone stale; curl's one-shot-per-invocation model never hit it.

Persistence

Neon Postgres — single jsonb table

collections(name text primary key, data jsonb, updated_at) — one row per logical collection (journal, playbook, shadow, debates, beliefs, theses, secrets), upserted via INSERT … ON CONFLICT DO UPDATE.

Why a KV table, not a normalized schema: eight modules already had a stable JSON shape from their file-backed era; swapping Path.read_text()/write_text() for store().load()/save() was a two-line change per module instead of a schema migration.

Order safety

risk_gate.py + idempotent ref_id

Deterministic, no LLM in the loop: symbol whitelist, side whitelist (buy only), hard max quantity/notional, kill switch — evaluated on every order regardless of which path proposed it. Every placed order carries ref_id = uuid5(NAMESPACE_OID, journal_entry_id).

Why idempotency matters here specifically: both execution paths can legitimately retry on a transient MCP error; without a stable ref_id, a retry after an ambiguous failure could double-fill.

Runtime behavior, weekdays 8:45am Denver

01 · Engine

spy_decision_engine/main.py — pulls real OHLC/quotes via yfinance, computes a weighted momentum/sentiment/volatility score, writes final_decision.json-equivalent into the ledger. Deterministic; no model call.

02 · Debate

committee.py --once — Bull proposes, Bear rebuts the Bull's finished case, PM decides propose_trade or pass_with_reason. Every custom tool call is a journaled write, not free text.

03 · Execution decision

PM's propose_trade(mode="live") now routes through execute_autonomous(): risk_gate pass + notional ≤ $30 + SPY_LIVE=1 → real fill, no confirmation. Otherwise: status="proposed", queued.

04 · Sweep

sweep.py closes anything at target/stop/time-limit and resolves matured shadow trades + predictions from live quotes. Only covers status="open" (sim) entries — see the gap below.

Currently disarmed, and a known gap

SPY_LIVE is unset on the routine's environment, so execute_autonomous() always returns "not armed" — every proposal queues, same as before this capability existed. Separately: nothing in the codebase auto-closes a live position once opened — sweep.py's target/stop/time-limit logic only runs against sim-lane (status="open") entries. An autonomous fill accumulates as a real position until closed by hand via advisor.py.
